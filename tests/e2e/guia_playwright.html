🎭 Guía Definitiva: Tests E2E con Playwright

Bienvenido a la guía oficial de buenas prácticas para la creación y mantenimiento de pruebas End-to-End en el proyecto Gestor de Portafolios. Seguir esta guía garantiza que nuestras pruebas sean robustas, rápidas y fáciles de mantener.

💡 Principio de Oro (DRY): Don't Repeat Yourself (No te repitas). Si vas a escribir el mismo flujo más de dos veces (ej. Iniciar sesión, Navegar a un menú), muévelo a helpers.js.

1. Estructura y Ejecución de Pruebas

Los tests están divididos en carpetas según el Sprint. Cuando escribas un test nuevo, asegúrate de colocarlo en el Sprint que corresponde a la funcionalidad.

¿Cómo ejecutar los tests?

  • Todo el proyecto: npx playwright test
  • Modo visual (Interfaz): npx playwright test --ui
  • Test específico: npx playwright test tests/e2e/4to_Sprint/SMOKE_PROD.spec.js
  • Ejecutar contra producción: $env:BASE_URL="http://tis.cs.umss.edu.bo" ; npx playwright test

2. Aprovechando el Modo Interfaz Gráfica (UI Mode)

El UI Mode (npx playwright test --ui) es tu mejor aliado al momento de escribir, depurar y mantener las pruebas. En lugar de correr scripts a ciegas en la consola, obtienes un entorno de desarrollo completo. Principales ventajas:

  • Viaje en el Tiempo (Time Travel): Puedes revisar cada paso del test, ver cómo lucía el DOM, dónde hizo clic el puntero y qué red se estaba ejecutando en ese exacto milisegundo.
  • Selector Picker (Pick Locator): En lugar de adivinar el selector de un botón, puedes hacer clic sobre él en la vista previa del UI Mode y Playwright generará automáticamente la mejor aserción sugerida (ej. getByRole('button', { name: 'Entrar' })).
  • Watch Mode (Modo Observador): Si activas el ícono del ojo (👁️) al lado de un archivo de test, Playwright volverá a ejecutar esa prueba automáticamente en tiempo real cada vez que guardes cambios en tu código, haciendo el desarrollo de la prueba mucho más ágil.
  • Inspección de Red (Network): Cada paso captura el estado completo de la consola del navegador y de las peticiones Fetch/XHR, lo cual es vital para saber si un test falló por un problema de Frontend o porque la Base de Datos o API fallaron (ej. un Error 500).

3. Uso Correcto de helpers.js

Nunca hardcodees la URL (http://localhost:8000) dentro de los tests. Utiliza siempre la constante BASE del helper para permitir ejecuciones dinámicas.

// ❌ FORMA INCORRECTA
const BASE = 'http://localhost:8000';
await page.goto(BASE);

// ✅ FORMA CORRECTA
import { BASE, loginUsuario } from '../helpers.js';
await page.goto(BASE);

3. Localizadores (Selectores) — Buenas y Malas Prácticas

Playwright ofrece múltiples formas de encontrar elementos. Prioriza localizar elementos por cómo los ve el usuario (Accesibilidad) en lugar de depender de la estructura interna del HTML.

🏆 Excelente: page.getByRole('button', { name: 'Guardar' })
🥈 Muy Bueno: page.getByPlaceholder('ejemplo@gmail.com') o page.getByText('Bienvenido')
🥉 Aceptable (Si tiene ID): page.locator('#fNombre')
❌ Frágil y Propenso a fallar: page.locator('div.container > form > div:nth-child(2) > input')

4. Esperas Inteligentes vs Esperas Estáticas

NUNCA uses page.waitForTimeout(5000) a menos que sea estrictamente necesario (por ejemplo, esperar una animación caprichosa). Las esperas estáticas hacen que las pruebas sean extremadamente lentas.

// ❌ MALA PRÁCTICA: Perderás 5 segundos siempre, incluso si cargó en 0.5s.
await page.click('#btnSave');
await page.waitForTimeout(5000); 

// ✅ BUENA PRÁCTICA: Playwright esperará HASTA 5 segundos, pero si aparece en 0.1s, avanza inmediatamente.
await page.click('#btnSave');
await expect(page.locator('.alert-success')).toBeVisible({ timeout: 5000 });

Esperar peticiones de red

Si un botón dispara una petición Ajax/Fetch (ej. Guardar Perfil), la mejor manera de esperar a que termine es con networkidle (espera a que no haya tráfico de red) o esperando directamente el cambio visual.

await page.goto(BASE);
await page.waitForLoadState('networkidle'); // Espera a que termine de cargar recursos pesados

5. Estructura ideal de un Test Case (TC)

Un buen caso de prueba sigue el patrón AAA (Arrange, Act, Assert): Preparar, Actuar, Comprobar.

import { test, expect } from '@playwright/test';
import { BASE, loginUsuario } from '../helpers.js';

test.describe('Módulo de Ejemplo', () => {

    test('TC-01: Nombre descriptivo de lo que hace', async ({ page }) => {
        // 1. Arrange (Preparar entorno)
        await loginUsuario(page);
        await page.locator('#btn-seccion').click();
        
        // 2. Act (Acción del usuario)
        await page.fill('#fInput', 'Dato de Prueba');
        await page.click('#btn-guardar');

        // 3. Assert (Validación)
        await expect(page.locator('#mensajeExito')).toBeVisible();
        await expect(page.locator('#mensajeExito')).toContainText('Guardado con éxito');
    });

});

6. Limpieza (Teardown) y Aislamiento

Las pruebas deben ser completamente independientes. Si una prueba falla, no debe romper la siguiente.

  • No compartas el mismo estado de página entre tests (por defecto Playwright te da un page limpio en cada test()).
  • Si requieres hacer limpieza al terminar, usa test.afterEach(). Puedes importar logoutCleanup desde helpers.js para cerrar sesión de manera segura.
Resumen de comandos útiles de aserción:
  • expect(element).toBeVisible() — Está renderizado.
  • expect(element).toBeHidden() — No existe o está en display: none.
  • expect(element).toHaveText('Texto exacto')
  • expect(element).toContainText('Subtexto')
  • expect(element).toHaveClass(/error/) — Utiliza Regex para validar clases de CSS.
  • expect(page).toHaveURL(/.*\/ruta/) — Valida redirecciones.
